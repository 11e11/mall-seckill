# 秒杀超时关单库存回补

## 背景与范围

原链路先提交订单关单，再单独释放秒杀活动库存并直接递增 Redis。后一步失败时，订单已关闭，重复的延迟消息不会重新释放库存。本次只调整秒杀超时关单；主动取消和历史已关闭订单不在本次范围。

## 同步事务

延迟消息找到订单活动关联后，在订单取消锁内运行同一个 MySQL 事务：订单状态以 `101 → 103` 条件更新，释放活动库存关联 `LOCKED → RELEASED`，更新活动 SKU 的可售与冻结库存，写释放流水和 `SECKILL_REDIS_RELEASE:<orderSn>:<activitySkuId>` 本地消息。任一步失败则整个事务回滚。支付回调先把订单改为已支付时，关单条件更新失败，不会创建回补任务。普通 SKU 原有取消处理仍留在同一事务中。

## 异步回补与幂等

现有本地消息 relay 每 5 秒扫描待处理消息。新主题由本地处理器执行 Redis Lua：若操作标记已存在则视为完成；若秒杀入口库存 Key 缺失则失败并告警；否则原子地递增库存、清除用户抢购标记、写无过期时间的操作标记。处理器随后把秒杀轮询结果更新为已关闭，成功后由 relay 标记消息为已处理。

该主题超过普通消息的 5 次失败上限后继续自动重试，沿用最多 60 秒的退避间隔，并在第 5 次及之后每 10 次失败时记录错误日志。现有运营本地消息指标增加待回补任务数和最长等待秒数。若 Redis 数据丢失，库存 Key 缺失会暂停回补；需要先核对并重建 Redis 状态，再让任务继续。幂等标记在活动归档且任务全部处理完之前不能清理；运行中的全量库存预热仍可能覆盖入口余量，应避免在活动进行时执行。

## 验证与运维

定向测试覆盖支付与关单竞争的条件路径、活动库存释放、任务生成、Redis 回补返回码、重复消息和持续重试。构建时如使用 Java 21，需要临时指定兼容的 Lombok 版本 `-Dlombok.version=1.18.42`；仓库配置仍保持 Java 17。上线后关注 `ops/trade/local-message/metric` 的待回补数量和最长等待时间，以及 `SECKILL_REDIS_RELEASE` 主题的错误日志。
